# gfx studio ↔ T3 Code: connect, threads panel, send (spec v1)

This replaces docs/CLAUDE-IN-APP.md §4 (the webhook "Send to T3" and the "Open T3" link). The facts below come from
the T3 step-0 findings (`~/claudeStuff/gfx-step0/gfx-handoff.md`, 2026-10-15).

## 1. Model
- The T3 server runs in WSL and is reached from Windows at **`http://127.0.0.1:3773`**. Always use `127.0.0.1`,
  never `localhost`: OAuth `resource`/issuer and the cookie are tied to that host. The address is configurable in
  ⚙ → Integrations.
- **One gfx project = one T3 project.** The T3 project's `workspaceRoot` is the gfx project folder as a WSL path.
  The studio's "folder" (library of projects) is a path prefix: "all threads in this folder" means all T3 projects
  whose `workspaceRoot` starts with `<folder>/`.
- **Matching** (Rust `t3::match_project` + JS twin `matchProject`, unit-tested): the gfx project maps to the T3 project whose
  `workspaceRoot` equals its WSL path; else to the project with the **longest** `workspaceRoot` that is a parent of it
  (prefix + `/`: `/a/b` is not a parent of `/a/bc`); else, for a git worktree whose main repo is elsewhere (`.git` file →
  `gitdir: <main>/.git/worktrees/<name>`), the same two rules for the main repo root. Only without any match does the
  "not in T3 yet" / auto-create logic apply, so a worktree never gets a duplicate T3 project.
- Path mapping (Rust, unit-tested):
  - `C:\a\b` → `/mnt/c/a/b`;
  - `\\wsl.localhost\<distro>\x` and `\\wsl$\<distro>\x` → `/x`;
  - Linux paths (dev shim) stay as they are.

## 2. Connect (one time)
⚙ → Integrations → **Connect T3** (or the panel's Connect T3) shows two steps in the T3 panel. Each step takes its own
pairing link or code (T3 → Settings → Connections → create a pairing link); each works once.

**Why two codes:** a pairing code made with T3's default (standard) scopes signs a browser in, but that session has no
`access:write`, so it may not approve agents (`McpOAuth.approvingBrowserSession`). T3's approval page would then ask for
a second code anyway, typed into T3's page (and T3's "Create link" gives a URL from which the token must be cut by hand).
gfx asks for both in its own fields instead, accepts a whole link or a bare code, and explains why.

1. **Step 1 of 2 · Sign in the T3 view** (one field: "Paste the pairing link or code"). gfx takes the token from a
   pairing link (`#token=` in the hash, else `?token=` in the query, like T3's `getPairingTokenFromUrl`) or a bare
   code, and loads `<server>/pair#token=<code>` in the T3 view (§4), always built from the configured server: a pasted
   link's own host is never opened (it may be another address of the same T3; the token goes to the configured
   server either way). T3's `/pair` page signs itself in with a token in its URL (`PairingRouteSurface` auto-submits
   it). gfx then waits for `GET /api/auth/session` (with the view's cookie, from Rust) to report the view signed in.
   The cookie persists in the webview data dir, so the step is skipped (shown as done) when the view is signed in
   already.
2. **Step 2 of 2 · Approve gfx studio** (the access level + "Paste a second pairing link or code", with one line on
   why a second one is needed). Rust (`t3.rs`) approves gfx itself, without T3's approval page:
   - discover the server through `/.well-known/oauth-authorization-server`;
   - register dynamically once (`POST /oauth/mcp/register`, redirect URI `http://127.0.0.1/gfx-studio/callback`)
     and persist the signed `client_id`;
   - build PKCE S256 with `resource=http://127.0.0.1:3773/mcp` and scopes
     `orchestration:read orchestration:operate`;
   - `POST /oauth/mcp/decision` with `{ authorization: <the authorize request's query as an object>, decision:
     { _tag: "pairing-code", access, code } }` (`AuthMcpApprovalDecisionRequest`);
   - T3 answers `{ redirectTo }` = the redirect URI with `code`, `state` and `iss` (state and issuer checked; an
     `error` redirect is reported), or 400 `AuthMcpApprovalError { message }` (a used-up code, a code without the
     scopes for that access level, ...), shown under step 2 with the field kept for a new code;
   - Rust exchanges the code at `/oauth/mcp/token`.
   Nothing listens on the redirect URI and the view never shows T3's approval page.
   **Change access…** is step 2 only (the view stays signed in).
3. **Store the token.** The access token (30 days, no refresh) and its expiry go in the app config dir `t3.json`.
   They never go in a project, in logs or in the frontend: the frontend only gets `{ connected, level, expiresAt }`.
   On 401 or expiry the status becomes "Reconnect T3".

**Access level** (a user choice, changeable later; nothing assumes one user's setup):
- Before connecting, ⚙ → Integrations explains what each level allows in the studio:
  - **Read-only:** see threads and their status.
  - **Standard:** also send to and start threads.
  - **Full access:** also create T3 projects for gfx projects automatically.
- The level is picked in step 2 and sent as T3's `AuthMcpClientAccess`: Read-only = `read-only`, Standard =
  `auto-accept-edits` (T3's runtime ceiling for the threads gfx starts: edits auto-accepted, commands ask),
  Full access = `full-access`. The studio learns which level was granted from the scopes in the token response.
- The studio shows the current level and expiry, with **Change access…** (step 2 again with a new code; the new token
  replaces the old one) and **Disconnect** (forgets the token and `client_id` locally).
- Features adapt to the granted level:
  - Send and New thread are disabled with a tooltip below Standard.
  - Without full access, a gfx project without a T3 project shows "Add this folder in T3" (with the WSL path)
    instead of creating it.
- **Auto-create T3 projects** toggle: on by default when full access is granted, and can be turned off.
- Server address, level and toggle are stored in the app config dir, per machine.

## 3. MCP client (Rust)
- Streamable HTTP MCP on `POST /mcp` with `Authorization: Bearer`:
  - `initialize`, keeping `Mcp-Session-Id` if returned;
  - `tools/call`;
  - responses are either JSON or SSE (`text/event-stream`, using the last `message` event).
  - Built on `ureq`, like `http_post_json`.
- Tauri command `t3_call(tool, args)` with an **allowlist**:
  - `t3_environment_read`, `t3_project_list`, `t3_project_create`;
  - `t3_thread_list`, `t3_thread_read`, `t3_thread_wait`, `t3_thread_launch`, `t3_thread_send`;
  - `t3_attachment_prepare_upload`, `t3_thread_send_attachments`.

  No delete, archive, settle or interrupt tools: the studio never deletes T3 projects or threads.
- `t3_thread_launch` is not idempotent. After an error or timeout, check `t3_thread_list` (title + time) before
  retrying.
- `environmentId` is cached per server.

## 4. T3 panel (dock panel `t3`, docs/LAYOUT.md)
**Top: threads list.**
- Scope switch: **This project** | **All in folder** (grouped by project).
- Each row: status dot (running · waiting for you · done · failed · idle), title, relative time, model.
- **+ New thread** (current project) and a refresh button.
- Refresh with `t3_thread_list` every 5 s while the panel is visible, every 30 s while hidden. The top-bar T3 button
  shows a badge with the number of threads `waiting` for the user in this folder.
- If the current gfx project has no T3 project:
  - with full access and **Auto-create** on, it is created on first use (title = gfx project name);
  - otherwise the panel says "Add this folder in T3" and shows the WSL path.

**Bottom (or a tab): T3 view.**
- A native Tauri child webview (`unstable` feature) placed over the panel's rect: it follows `ResizeObserver` and
  panel visibility, and is hidden while a studio overlay (dialog, popover, menu) overlaps it, because native
  webviews draw above HTML.
- URL: `http://127.0.0.1:3773/<environmentId>/<threadId>?embed=compact`. The `embed` flag is ignored until the T3
  fork ships compact mode; until then it shows full T3 chrome.
- The view only ever shows a thread of this project (or T3's `/pair` during connect step 1), never T3's root: T3's
  index route drops into a draft thread of the most recently used project, so a new gfx project would show another
  project's composer. With no thread open the native view is hidden and the panel shows its own placeholder:
  "Pick a thread or + New thread" when the project is in T3, "This project is not in T3 yet: + New thread adds it"
  (Full access + Auto-create) or "…: add this folder in T3 (see above)" when it isn't.
- **Fallback** if the spike fails (child webview can't track the dock reliably): the T3 view opens as a separate
  studio window "T3 · <project>", which can be tiled next to the main window.
- **Dev shim** (Linux browser): no native webview, so the panel shows the threads list plus an "Open in browser"
  link.

## 5. Send to T3 (Ask Claude → T3)
- The Ask Claude composer's **T3** button lets the user pick a target:
  - the thread open in the T3 panel (default);
  - another thread in this project;
  - **New thread**.
- Content:
  - the `gfx context` brief + the user's message (as today);
  - attachments: the frame at the playhead (PNG still) and the markup PNGs of the included comments. These go
    through `t3_attachment_prepare_upload` → upload (Rust PUT) → `t3_thread_send_attachments`, or as `attachments`
    on `t3_thread_launch`.
- After sending:
  - the comment gets the ✈ marker (as today);
  - the T3 panel opens that thread;
  - the thread row shows running → done;
  - on done, a toast "Claude finished: <title>" appears. Live reload and comment resolve already happen through
    files.
- **Open T3** in the top bar now opens and focuses the T3 panel (badge as in §4).
- Removed: webhook URL, thread link and send mode settings (old values ignored).

### T3 fork findings (from the real-app walkthrough, for the user to dispatch to the fork)
1. **Enter adds a newline in a narrow embedded panel** (2026-10-16). In `apps/web/src/composer-logic.ts:50`
   (`composerSubmissionIntentForKey`), `isMobileViewport` (`useMediaQuery("max-sm")`, under about 640 px) turns off keyboard
   submit, so Enter inserts a newline and no key sends. Docked in gfx, the T3 panel is narrower than that; full screen it
   sends.
   - Fix: in `?embed=compact` (or generally), decide by input type (`(pointer: coarse)`), not by width, so a narrow
     desktop panel still sends with Enter.
   - Workaround: click ↑, or widen the panel past about 640 px.
2. **Add project doubles the home path when an absolute path is pasted** (2026-10-16).
   - Cause: the palette prefills `~/` (`CommandPalette.tsx:1055-1063`, or `addProjectBaseDirectory`), so a pasted
     `/home/<you>/x` becomes `~//home/<you>/x`. Then `expandHomePath` (`apps/server/src/os-jank.ts:93-103`, twin
     `packages/provider-core/src/server/pathExpansion.ts:17-24`) does `join(home, input.slice(2))`, which gives
     `/home/<you>/home/<you>/x`. `createWorkspaceRootIfMissing` then creates that empty folder.
   - Fix: when the rest after `~/` is already absolute, use it as is. Also have the palette replace the prefill when an
     absolute path is pasted. `WorkspaceEntries.ts:121-123` (browse) has the same shape.
   - Workaround: clear `~/` before pasting.
3. **No link opens a native new-thread draft in a chosen project or worktree** (2026-10-16).
   - gfx's + New thread calls `t3_thread_launch`. An MCP client has no caller thread to inherit a model from, so T3
     requires `modelSelection` when the project has no default model (`apps/server/src/mcp/toolkits/project/handlers.ts:127-137`).
     The user wants to pick the model and reasoning in T3's own composer instead of in gfx.
   - Today: `/new` (`packages/shared/src/promptLinks.ts`, `parseNewThreadLink`) needs a prompt and only names a GitHub
     repo; `/projects/$projectKey` redirects to settings; `/` opens a draft in the last-used project.
   - Fix: `/new?project=<projectId>[&worktree=<absolute path>]` with the prompt optional opens the normal draft in that
     project (and existing worktree) through `handleNewThread`, as `NewThreadLinkView.openDraft` already does. It should
     work in `?embed=compact`.
   - gfx after the fork: + New thread loads that URL in the view (no title row; T3's composer picks model, reasoning
     and checkout). Until then: gfx passes the model of the project's most recent thread, else `claudeAgent` /
     `claude-opus-5-5`.
4. **An MCP client can't revoke its own token** (2026-10-16). Each gfx Connect / Change access / reconnect leaves an
   extra "gfx studio" client in Settings → Connections, because `/api/auth/clients/revoke` needs `access:write` and there
   is no OAuth token revocation for MCP clients. Fix: an RFC 7009 style `POST /oauth/mcp/revoke` (advertised as
   `revocation_endpoint`) that lets a bearer revoke its own grant. Optionally, re-approving the same client id should
   replace its earlier grant instead of adding one.
